# Aether project instructions

- The canonical product name is **漫频 Aether**. The project directory and repository name are `Aether`; the repository is `dpan538/Aether`. Preserve the approved wording in `branding/README.md`.
- **Aether is a visually driven project specializing in visual listening experiences, not a comprehensive radio utility.** Let each page's visual purpose guide feature selection. Do not expand the feature set merely to populate reference controls or compete on completeness.
- The project entered planning and design on 2026-10-24. Read `docs/PRODUCT-SCOPE.md`, `docs/EXPERIENCE-PLAN.md` and `docs/DECISIONS.md` before making project changes. Continue the phase requested by the user; do not treat repository initialization as a request to build UI or scaffold an Android app.
- The user has fixed **three pages with three distinct UIs**: immersive playback based on references 1/2, a richly controlled retro page based on reference 3, and the **modern main page** based on reference 4. The modern page has a lower console and an upper station-filter screen matching the reference's blue display; it also hosts settings. Read `design/README.md` and `docs/PAGE-ELEMENTS.md`. Navigation and detailed control mappings remain undecided; do not impose BARO's two-page swipe rules.
- Preserve all four supplied originals under `design/references/2026-10-24/`, with their source manifest. They are authorized design references, not original Aether UI or shipping assets. Do not replace or modify them when creating later designs. Unrelated private screenshots remain excluded.
- Separate user-confirmed requirements, assistant proposals and implemented behavior. Do not silently freeze proposed sort orders, pause policies, platforms, navigation, licensing or optional features as approved decisions. New user instructions take precedence and can advance the phase without a separate approval ritual.
- Aether is the standalone radio product. Keep the future local-music/external-player suite separate. Do not import Annota or BARO code, keys, assets, project rules or existing UI constraints merely because they are neighboring projects.
- Preserve neutral indexing: no advertising placements, popularity charts, paid ranking, recommendation feed or algorithmic personalization. User-triggered random exploration is part of the requested scope. Public ordering rules remain undecided.
- Treat station identity, station streams, live status, connection quality and audio level as distinct concepts. Never invent city, timezone, artwork provenance, current program, bitrate, packet loss or precise latency. Conditional data must have a natural missing-data state.
- Playback enumeration and regression belong to implementation and verification. A hand-maintained station sample table is not a prerequisite for product planning. Document actual tested environments and coverage; never claim worldwide availability from a limited probe or native-device behavior from browser output.
- Keep documentation useful and truthful. For documentation-only work, check links, consistency, whitespace and the resulting Git diff. Do not add application tests or fake build/status badges for a project with no implementation.
- Each pushed commit should have an informative English title and a body explaining changes and actual validation, ending with a short Chinese summary. Keep the repository's current status visible in README and decision records.
- Keep secrets, credentials, private screenshots, personal local paths, SDKs, signing keys, caches and generated packages out of Git. Licensing is undecided; do not grant a code or brand license without a user decision.
